# 架构决策记录 (ADRs)

本文档记录 FlowUs Limbic 项目的重要架构决策。

## ADR-001: 使用 esbuild 作为构建工具

**日期**: 2024-01-15
**状态**: 已采纳

### 上下文

Obsidian 插件需要打包为单个 JavaScript 文件。需要选择一个构建工具。

### 选项

1. **Webpack** - 功能强大，配置复杂
2. **Rollup** - 适合库，Tree Shaking 好
3. **esbuild** - 极快，简单
4. **Vite** - 基于 esbuild，开发体验好

### 决策

选择 **esbuild**。

### 理由

- **速度**: esbuild 比 Webpack/Rollup 快 10-100 倍
- **简单**: 配置简单，易于维护
- **Obsidian 生态**: 大多数 Obsidian 插件使用 esbuild
- **内置 TypeScript**: 无需额外配置
- **满足需求**: 插件不需要复杂的代码分割等特性

### 结果

- 构建时间 < 1s
- 配置文件 < 50 行
- 开发体验良好

## ADR-002: 使用 TypeScript 严格模式

**日期**: 2024-01-15
**状态**: 已采纳

### 上下文

需要决定 TypeScript 的严格程度。

### 选项

1. **宽松模式** - 快速开发，类型检查少
2. **严格模式** - `strict: true`
3. **超严格模式** - 开启所有可能的检查

### 决策

选择 **严格模式** (`strict: true`)。

### 理由

- **类型安全**: 减少运行时错误
- **IDE 支持**: 更好的自动补全和重构
- **可维护性**: 代码更易理解和修改
- **不是太严格**: 保持一定的灵活性
- **Obsidian API**: Obsidian 提供了完整的类型定义

### 结果

- 更少的运行时错误
- 更好的开发体验
- 学习成本适中

## ADR-003: 使用 tsyringe 进行依赖注入

**日期**: 2024-01-20
**状态**: 已采纳

### 上下文

需要管理组件之间的依赖关系，提高可测试性。

### 选项

1. **手动构造** - 简单，不灵活
2. **tsyringe** - 轻量级，装饰器风格
3. **inversify** - 功能强大，较复杂
4. **Awilix** - 功能强大，较大

### 决策

选择 **tsyringe**。

### 理由

- **轻量级**: 体积小，依赖少
- **装饰器风格**: 代码简洁
- **TypeScript 友好**: 类型安全
- **足够强大**: 满足插件需求
- **活跃维护**: 社区活跃

### 结果

- 代码更易测试
- 依赖关系清晰
- 组件解耦良好

## ADR-004: Schema 驱动的数据转换

**日期**: 2024-01-25
**状态**: 已采纳

### 上下文

需要支持多种数据类型（TODO、笔记等）与 FlowUs Block 之间的转换。

### 选项

1. **硬编码转换** - 简单，难扩展
2. **策略模式** - 每个类型一个转换器
3. **Schema 驱动** - 声明式定义转换规则
4. **代码生成** - 根据定义生成代码

### 决策

选择 **Schema 驱动**。

### 理由

- **零代码侵入**: 添加新类型不需要修改核心代码
- **声明式**: 易于理解和维护
- **类型安全**: TypeScript 类型检查
- **可测试**: 每个 Schema 可独立测试
- **可组合**: Schema 可以组合和重用

### 结果

- 易于扩展新数据类型
- 核心代码稳定
- 良好的可维护性

## ADR-005: 分层架构设计

**日期**: 2024-02-01
**状态**: 已采纳

### 上下文

需要设计整体架构，确保关注点分离。

### 选项

1. **单层架构** - 所有代码在一起
2. **三层架构** - UI、业务逻辑、数据访问
3. **分层架构** - 通用同步层、适配层、应用层
4. **六边形架构** - 依赖倒置

### 决策

选择 **分层架构**。

### 架构

```
┌─────────────────────────────────┐
│      应用层 (Presentation)       │
│  (Obsidian UI, CLI, etc.)       │
├─────────────────────────────────┤
│    通用同步层 (Universal Sync)   │
│  (Entity, Transformer, Sync)    │
├─────────────────────────────────┤
│      适配层 (Adapter Layer)      │
│  (FlowUs API, Storage)          │
├─────────────────────────────────┤
│      外部服务 (External)        │
│  (FlowUs Platform)              │
└─────────────────────────────────┘
```

### 理由

- **关注点分离**: 每层负责单一职责
- **可复用**: 通用同步层可用于其他平台
- **可替换**: 适配层可以替换为其他平台
- **可测试**: 每层可独立测试
- **演进友好**: 可以逐步添加新功能

### 结果

- 架构清晰
- 易于维护
- 便于扩展

## ADR-006: 使用 OAuth 2.0 Authorization Code Flow

**日期**: 2024-02-05
**状态**: 已采纳

### 上下文

需要安全地认证 FlowUs API。

### 选项

1. **API Key** - 简单，不安全
2. **Implicit Flow** - 不支持刷新令牌
3. **Authorization Code Flow** - 最安全
4. **Password Flow** - 不推荐

### 决策

选择 **Authorization Code Flow** + **PKCE**。

### 理由

- **安全性**: 最安全的 OAuth 流程
- **刷新令牌**: 支持长期使用
- **PKCE**: 增强公共客户端安全性
- **FlowUs 支持**: FlowUs API 完全支持

### 结果

- 安全的认证
- 良好的用户体验
- 符合安全最佳实践

## ADR-007: 增量同步策略

**日期**: 2024-02-10
**状态**: 已采纳

### 上下文

需要高效地同步数据，减少 API 调用。

### 选项

1. **全量同步** - 每次同步所有数据
2. **增量同步** - 只同步变更
3. **事件驱动** - Webhook 实时推送
4. **混合** - 增量 + 定期全量

### 决策

选择 **增量同步** + **定期全量校验**。

### 策略

- **时间戳**: 使用 `updatedAt` 检测变更
- **指纹**: 使用内容指纹检测变更
- **游标**: 使用 API 游标分页
- **校验**: 每天一次全量校验

### 理由

- **效率**: 最小化 API 调用
- **实时性**: 可配置同步间隔
- **可靠性**: 定期全量校验确保一致性
- **FlowUs API 支持**: API 支持按时间查询

### 结果

- 快速同步
- 低 API 消耗
- 数据一致性

## ADR-008: 文档结构设计

**日期**: 2024-02-15
**状态**: 已采纳

### 上下文

需要组织文档，让用户和开发者都能快速上手。

### 选项

1. **单层结构** - 所有文档在一起
2. **按用户类型** - 用户文档 / 开发者文档
3. **按主题** - 功能 / 配置 / 架构 / etc.
4. **混合** - 多层分类

### 决策

选择 **混合结构**。

### 结构

```
docs/
├── README.md                    # 文档首页
├── getting-started/             # 入门指南
├── features/                    # 功能文档
├── configuration/               # 配置指南
├── troubleshooting/             # 故障排除
├── architecture/                # 架构文档
├── development/                 # 开发者文档
├── reference/                   # 参考文档
├── faq.md                       # 常见问题
└── releases/                    # 发布说明
```

### 理由

- **清晰**: 用户可以快速找到所需内容
- **分层**: 从入门到深入
- **完整**: 涵盖用户和开发者需求
- **可扩展**: 易于添加新文档

### 结果

- 良好的文档体验
- 用户和开发者都能快速上手
